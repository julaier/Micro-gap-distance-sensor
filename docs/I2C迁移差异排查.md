# I2C 迁移差异排查（更新于 2026-11-13）

## 已核对的事实

原工程 `D:/Codex_Workspace/new` 未改动。
原工程和 C011 工程的 `Device/ldc1614.c` SHA-256 相同：
`4035FE25EB5361D82E91F46835455D58F7B1F96D950E8980FFCB71C879829B98`。

| 项目 | 能运行的 F103 工程 | C011 V2 工程 | 核对结果 |
| --- | --- | --- | --- |
| 地址 | 7 位 0x2A，发送前左移 1 | 相同，实际写地址 0x54、读地址 0x55 | 未发现移位差异 |
| 复位 | 写 0x1C、0x80、0x00 | 相同 | 未发现寄存器序列差异 |
| ID | 先写寄存器地址，再重复 START 读两字节 | 相同的总线操作 | 独立从机模型可读出 0x5449 / 0x3055 |
| ACK | 硬件 I2C 完成第 9 个时钟的采样 | SDA 开漏释放，第 9 个时钟采样 | 独立从机模型可正常应答 |
| SCL | SPL 按 PCLK 配置硬件 100 kHz | GPIO 软件时序，每个半周期调用通用微秒延时 | 真实周期不能仅由 5 μs 参数推算 |
| 计时开销 | 硬件传输不依赖通用微秒延时 | 反汇编显示每次延时调用软件除法，且逐微秒循环 | V3 已替换为 TIM14 连续计数 |
| 上电前置流程 | 初始化 OLED 并传送整屏数据 | OLED 调用注释 | V2 起已显式补充 100 ms 等待 |

实板 V2 日志中的 `-2,ADDR_W` 表示在地址阶段未读到 ACK；
不能单凭这一点证明问题在硬件，也不能证明软件产生的实际波形满足器件要求。
TI SNOSCY9A 第 7 页规定 LDC1614 的 SCL 频率为 10～400 kHz。

## V3 的处理

- 保持实物接线 PB7=SCL、PB6=SDA，保持 HSE 8 MHz。
- TIM14 以 1 MHz 计数；延时及拉伸超时不再依赖通用延时和 SysTick 毫秒函数。
- 用 `$T` 报告该字节内的 SCL 周期最小值、最大值和时钟数。
- 保留 V2 的首次失败阶段、电平和 GPIO 自检，OLED 初始化仍为注释。
- 新增独立开漏从机模型：根据实际地址、数据和时钟边沿应答，而不是预设 ACK。

## 验证范围与尚未确认的结论

两套主机测试通过；Keil 编译通过。
反汇编确认 V3 的字节传输不再调用 `board_delay_us` / `__aeabi_uidiv`，
使用 TIM14 的 CNT 地址 `0x40002024`。

独立数字模型在 V2、V3 都能正常完成传输，因此不能声称已发现地址拼接、
位数或重复 START 的确定错误。V3 修正了软件计时实现并增加实际周期观察，
但 V2 的实际 SCL 频率尚未在板上测得，不能断言其低于 10 kHz，
也不能把软件延时开销认定为已确认的实板 NACK 根因。

## V3 实板结果与 V4 对照

用户后续截图显示：版本为 `C011_SW_I2C_PB7_PB6_V3_TIM14`，首次错误
`-2,ADDR_W,0,2`；初始化和 0x2A～0x2D 探测的 `$T` 均为 `19,24,9`。
即本机计时约 42～53 kHz，但地址 ACK 仍未成功；前述“延时过慢”猜测没有
得到这次日志的支持。`lines=2` 是拉低 SCL 后的现场，不等于 ACK 瞬间的电平。

已继续核对 LL GPIO 初始化与位操作、GPIOB/TIM14 地址、数据最高位先发、
START/STOP、重复 START 和 SDA 开漏释放；未发现能解释全部地址 NACK 的确定错误。
对旧图还须保留一项歧义：MCU 符号中 PB7 连的是名为 PB6 的网络，PB6 反之。
用户指定 PB7=SCL/PB6=SDA 不变，不能凭图上网络名静默改变生产映射。

V4 因此增加诊断，而不是宣称已修复：

- 发送的 8 位均在 SCL 高期间从 IDR 采样，报告待发字节与采样字节；
- 第 9 拍前、中、末三点 SDA 采样，保留末次 ACK 判据；
- 实读 ACK 阶段的 MODER/OTYPER，区分输入、开漏和推挽配置；
- 同一驱动逐项对照两种映射、OD/显式输入接收、0x2A/0x2B 地址，只读两个 ID；
- 诊断结束显式恢复用户指定映射，保留原初始化故障，不自动回避 NACK。

两套主机测试通过，包含四种映射/方向组合、错误映射拒绝、ID 读回、
数据读回差异注入、ACK 三点差异与显式输入后的超时恢复。
Keil 完整编译为 0 错误、0 警告，Code=29840 / RO=480 / RW=16 / ZI=2288。
数字模型不能证明真实引脚的模拟波形；当前还需要 V4 实板日志才能进一步区分。

## V5：100 kHz 受控对比（2026-11-13）

V4 后续实板日志的 SCL 周期约为 24～28 μs，约 36～42 kHz。
这在器件允许范围内，尚不能认定频率就是地址 NACK 的根因。本次按用户
要求向原 F103 的 100 kHz 靠拢，保持 PB7=SCL、PB6=SDA 和原 LDC 寄存器流程。

- TIM14 提高到 4 MHz，使用 16 位差值处理回绕；10 ms 拉伸超时为 40000 ticks。
- 每半拍从刚确认的边沿开始等待；处理耗时过长时延长当前拍，不压缩下一半拍。
- 记录 9 个原始时间戳，字节结束后统计周期，避免逐拍统计继续拖慢 SCL。
- 上电稳定后仅发送地址探测，枚举半拍等待预算，选择最接近 100 kHz 的结果。
  NACK 仍保留真实错误；SCL/总线异常停止校准，不写 LDC 寄存器。
- 正常字节期间保存 PRIMASK 并屏蔽中断，结束时恢复原状态；SCL 拉伸期间
  恢复原状态再等待，避免整个 10 ms 超时都屏蔽 SysTick。
- `$T` 保留原有字段，追加 0.1 μs 周期、实际平均 Hz 和等待 tick 数。
  `$T,CAL,...` 始终输出校准结果，不能只依据 `I2C_TARGET_HZ` 判断实际频率。
- V4 的接线矩阵源码保留，V5 默认关闭；初始化错误、线电平、发送读回、
  ACK 三点采样和地址探测继续保留，OLED 初始化调用继续注释。

主机测试覆盖协议、超时/恢复、回绕、中断状态恢复、时钟拉伸和 ACK/NACK 校准。
独立从机模型加入每次 GPIO 调用 0.75 μs 开销后，校准为约 99071 Hz，仍能读出
ID 5449 / 3055；这是数字模型结果，实际板卡频率须查看新固件的 `$T` 输出。
版本标记为 `C011_SW_I2C_V5_TARGET100K`。尚未连接实板验证，不能宣称已解决 NACK。

## V6：固定引脚与整周期调度

- 正常构建固定 PB7=SCL、PB6=SDA，取消每拍动态映射开销。
- 不再对高、低两半拍分别叠加完整等待；按前一次上升确认点调度下一次上升，
  将处理时间计入整周期预算，同时独立保证高、低电平至少等待 6 ticks
  （1.5 μs）及发送 SDA 建立等待 1 tick（0.25 μs）。
- 保留 4 MHz TIM14、校准、ACK/NACK 判据、拉伸超时及中断状态恢复；
  `half_ticks` 现在表示整周期目标预算的一半，不是实际高/低电平时长。
- `$B,I2C_CAL,IN_RANGE` 表示完成 9 拍且统计为 90～110 kHz，否则为
  `OUT_OF_RANGE`；它不是 ACK 成功标志。
- 新增 `$D,PRE_ID,<mid_rc>,<mid_hex>,<did_rc>,<did_hex>`，在软复位和
  参考时钟配置之前只读 ID。正常为 `0,5449,0,3055`；失败时 `0000`
  是占位，不能当成实际寄存器内容。原 `Device/ldc1614.c` 仍与旧工程相同。
- 交叉映射源码保留，只有同时启用 `APP_I2C_MATRIX=1` 和
  `HARD_I2C_DIAGNOSTIC_MATRIX=1` 才运行；默认不自动换脚或更改地址。
- OLED 初始化及显示调用继续保持注释。

重新联合核对用户此前的两张原理图：MCU 实际 PB7 连到名为 PB6 的网络，
该网络接 LDC 的 SCL；MCU 实际 PB6 连到名为 PB7 的网络，该网络接 SDA。
跨页网络名与端口名不同，但两张图共同支持用户指定的 PB7=SCL、PB6=SDA。
用户确认仍使用原来正常工作的同一块 LDC 模块；原理图不能代替当前连接验证。

主机端协议测试、独立从机测试及启用交叉映射的独立从机测试均通过，
均使用 `-Wall -Wextra -Werror`。独立模型模拟每次 GPIO 调用 0.75 μs
开销后得到约 101587 Hz，仍能读出 5449 / 3055；这不是实板测量。
Keil 完整编译为 0 错误、0 警告，Code=30932 / RO=512 / RW=12 / ZI=2348。

版本标记为 `C011_SW_I2C_V6_FIXED_PINS`。用户目前没有示波器或逻辑分析仪，
下一步先查看这一版的完整启动串口输出，尤其是 `$T,CAL`、`I2C_CAL`
和 `PRE_ID`。地址 NACK 的根因仍未确认，V6 也尚未在用户板上验证。

## V6_NOCAL 实板结果与 V7 地址扫描（2026-11-13）

用户提供的 V6_NOCAL 日志已确认跳过校准，但仍为：

```text
$B,I2C_CAL,SKIPPED
$D,PRE_ID,-2,0000,-2,0000
$X,INIT,-2,ADDR_W,0,2
$T,INIT,14,15,9,138,148,68817,20
$W,INIT,54,54,7,1,1
```

因此，关闭校准这次没有改善地址 ACK，不能把校准认定为已确认的根因。
按用户“地址发送可以把所有情况都试着发送一下”的要求，V7 扩大地址探测：

- 版本标记为 `C011_SW_I2C_V7_SCAN7`。
- 只在初始化失败后，依次探测 `0x08～0x77` 共 112 个普通 7 位写地址；
  跳过保留地址，不扫描读方向、不发送寄存器或数据，也不自动改设备地址。
- `0x2A` 对应写地址字节 `0x54`，7 位地址 `0x54` 对应写地址字节 `0xA8`，
  两者均包含在扫描中，以覆盖地址表达方式混淆的情况。
- `$B,SCAN_BEGIN,08,77,W` 开始；每项输出
  `$S,<addr7>,<expected_write_byte>,<rc>,<stage>,<sampled_byte>,<ack_mask>,<lines>`。
  地址和两个字节为十六进制，其余数字为十进制；`START` 失败时，
  `expected_write_byte` 仅为计划值，不表示已发出。
- `$B,SCAN_DONE,112,<成功数>,<NACK数>,<其他错误数>` 结束；
  `rc=0` 为成功、`-2` 为 NACK，其余归入错误。仅 ACK 不足以认定找到 LDC1614。
- 保留 2A～2D 的旧 `$P` / `$X` / `$T` 输出；保留 PRE_ID、100 ms 等待、
  关闭校准的设置、引脚、时钟和 LDC 寄存器流程。OLED 调用继续保持注释。

独立从机模型新增完整地址扫描验证，检查每个地址对应的线上字节、9 拍、
ACK/NACK、总线释放和寄存器不变；生产构建和启用交叉映射的模型均通过。
新增 `test_app_scan.c` 直接执行应用的实际扫描函数，检查 112 项遍历、
边界地址、2A/54 应答、全 NACK、混合及全总线错误场景下的输出和汇总。
以上测试及原协议测试均以 `-Wall -Wextra -Werror` 编译通过。

新增扫描最初使程序侵入最后一页参数区；已通过共用应用层的十进制和十六进制
格式化函数消除重复展开，不改 I2C 位时序。最终程序不占参数页，避免现有
`CALS` / `CLR` 保存命令擦到程序。

Keil 完整编译 0 错误、0 警告，Code=28380 / RO=512 / RW=12 / ZI=2348。
